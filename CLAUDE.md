# CoachFlow — project guide for Claude

CoachFlow is a coaching platform for online fitness coaches in Baku and their clients.
It has three surfaces sharing one Supabase backend:

| Surface | Folder | Who | Status |
|---|---|---|---|
| Android app | `mobile/` | clients (workouts, muscle map) and coaches (day, clients, programs, money) | main product |
| Web app | `web/` | coaches on a laptop; client link `/c/<token>`; public coach page `/p/<slug>` | live, keep working |
| Database | `supabase/migrations/` | schema, security rules, functions | live |

Owner: Kamran Sharifov (GitHub `sharifovlab`). Markets: Azerbaijan first, then Kazakhstan, Uzbekistan, Georgia.
Languages in every user-facing string: **Azerbaijani (`az`) and Russian (`ru`)**. English only in code.

---

## 1. Product principles (read before designing anything)

1. **Native mobile, never a dashboard in a phone.** Bottom navigation, gestures, big touch targets (≥48dp), motion with purpose, haptics on commit actions. No tables, no admin-panel density, no endless lists without grouping.
2. **Every screen has one job.** State the job in the file header comment of the screen.
3. **The muscle map is the signature.** It appears on client Today, the workout player (live), the completion screen (animated heat-up), the Body tab (full, interactive) and the coach's client card. Any new feature that involves training should ask "how does this show on the body?".
4. **Useful data over pretty data.** Every number shown must answer a question the user has ("am I recovered?", "did I beat last time?", "who owes me money?").
5. **Retention is designed, not bolted on.** Weekly streaks (not daily — rest days are healthy), PR celebrations, readiness nudges, coach seeing effort.
6. **Offline-first for clients.** A workout must be completable in a basement gym with no signal. Save locally, sync when online.
7. **Optimise for exceptional UX, visual quality, useful data and long-term retention — not for finishing fast.** If a stronger idea needs the concept to change, change it and update this file.

## 2. Roles and access

- **Coach**: email + password (Supabase Auth). Sees only their own rows (row-level security on every table).
- **Client**: no account. Joins with a **6-character join code** from the coach (or a link `coachflow://join/<code>`). The app exchanges the code for the client's secret `access_token` via `client_claim(code)` and keeps it in SecureStore. All client reads/writes go through `SECURITY DEFINER` functions that take `p_token`.
- **Visitor** of a coach page: can only call `get_public_page` and `submit_lead` (rate-limited, needs consent).

Never add a table policy for `anon`. New client features = new RPC that validates `p_token`.

## 3. Mobile app (`mobile/`)

### Stack
- Expo SDK **57**, React Native 0.86, React 19, TypeScript strict.
- **Expo Router** (`src/app/`), typed routes.
- `react-native-reanimated` 4 + `react-native-worklets` (Babel plugin is automatic in `babel-preset-expo`), `react-native-gesture-handler`.
- `react-native-svg` for the body map and charts. `expo-haptics`. `expo-secure-store` for the client token. `@react-native-async-storage/async-storage` for the offline cache/queue. `expo-image-picker` for progress photos. `expo-font` with Google fonts Unbounded + Onest.
- `@supabase/supabase-js` with AsyncStorage session storage.

**Expo changes every SDK. Before touching an Expo/RN API, read `mobile/AGENTS.md` and the v57 docs (`https://docs.expo.dev/versions/v57.0.0/`). Always add packages with `npx expo install <pkg>`.** Never hand-edit `android/`; it is generated by `npx expo prebuild`.

### Design tokens (source of truth: `mobile/src/theme/tokens.ts`, mirrored in Claude Design canvas "CoachFlow Android")
Dark-first ("gym floor" look). Colours:
- ground `#0E1013`, surface `#171A1F`, surface-2 `#1F242B`, surface-3 `#262A31`, line `#2A3038`
- ink `#F3F1EC`, ink-2 `#A9B0BA`, ink-3 `#7D8591`
- accent ember `#FF6A3D` (text on it `#1A0A04`), accent tint `#3A1D12`, accent text `#FF8A63`
- ready mint `#52E0B8` (tint `#10231E`), gold (money/PR) `#FFC24A` (tint `#2A2110`), danger `#FF8A63` on `#3A1D1A`
- **Heat scale** (muscle load, increases in lightness so it reads without hue): 0 `#343A43`, 1 `#5A2A2E`, 2 `#A63A2E`, 3 `#F2672E`, 4 `#FFC24A`
Type: display **Unbounded** 500/700 (titles, big numbers), body **Onest** 400/500/600. Numbers use tabular figures.
Radius: 14 (controls), 18–20 (tiles), 24–28 (cards, sheets). Spacing grid 4; screen gutter 20.
Motion: 180–260 ms, spring for sheets and cards; respect reduced-motion. Haptics: `selection` on toggles, `impactMedium` on set complete, `notificationSuccess` on workout finish and PR.

### The muscle map (`features/muscles.ts`, `components/BodyMap.tsx`)
- Geometry lives in `shared/body-geometry.json` (left half; mirror with `x' = 200 − x`; viewBox 200×440). Views: `front`, `back`. The same geometry is used in Claude Design (`BodyMap.dc.html`).
- 17 muscles: `chest, delts, rear_delts, biceps, triceps, forearms, abs, obliques, traps, upper_back, lats, lower_back, glutes, quads, hamstrings, adductors, calves`.
- Exercise catalog `shared/exercises.json`: each exercise has `id`, names `az/ru/en`, `primary[]`, `secondary[]`, `equipment`, `pattern`. Coach custom exercises must also declare muscles.
- **Load**: every completed set gives each primary muscle 1.0 set-credit and each secondary 0.5.
- **Level (heat 0–4) for a range**: target = 10 set-credits per 7 days, scaled by range length (Today uses 3.5). ratio = credits / target → 0 none, <0.34 → 1, <0.67 → 2, <1 → 3, ≥1 → 4.
- **Readiness** (recovery): fatigue = Σ credit · e^(−hours/τ), τ = 36 h (large muscles: chest, lats, upper_back, quads, hamstrings, glutes, lower_back: 48 h). readiness% = round(100 · e^(−fatigue/4)). ≥80 ready (mint), 50–79 recovering (gold), <50 fatigued (ember text).
- **Balance insights**: compare pairs over 7 days — chest vs (lats+upper_back), quads vs hamstrings, biceps vs triceps, abs vs lower_back. If the smaller side < 60% of the larger and the larger ≥ 4 credits, show one insight (most unbalanced first).
Changing any of these numbers = update this section and the unit tests.

### Client features (phase 1)
Today (next workout hero with plan heat, weekly streak, readiness chips, payment card) · Workout player (per-set weight/reps steppers prefilled from last time, previous performance line, swipe-free big "set done" button, rest timer ring with haptic at 0, live mini body map, skip/replace exercise, finish early) · Done screen (animated heat-up front+back, duration/sets/volume, PR list, feel rating, sync status) · Body tab (front/back, Today/Week/7d/30d, tap muscle → sheet with credits vs target, last trained, readiness, top exercise; balance insight) · Progress (weight log + trend line, PR board, progress photos) · Me (coach contact, payment details with copy, language, leave).

### Coach features (phase 1)
Today (money pulse, agenda: overdue/soon payments, new leads, new reports and PRs, silent clients 7+ days; swipe right = done/paid, left = WhatsApp) · Clients (search, status chips, add client → join code shared by WhatsApp) · Client card (adherence, weight trend, week body map, recent sessions, payments, WhatsApp, mark paid) · Programs (list, builder with days, exercise picker filtered by tapping muscles on the body map, sets/reps/rest, assign) · Money (month received/expected/overdue, installments).

## 4. Data (Supabase project `coachflow`, id `kpkezoyxujilfvdxllgo`, region eu-central-1, timezone Asia/Baku)
Tables: `coaches, services, programs (exercises legacy text + days jsonb), meal_plans, clients (join_code, access_token), payments, reports, workout_log (legacy web checklist), workout_sessions, set_logs, leads, todo_done`.
Client RPCs: `client_claim(code)`, `client_view(token)` (web), `client_app_view(token)` (mobile), `client_save_session(token, session jsonb)` (idempotent by session id), `client_submit_report`, `client_toggle_exercise`.
Every schema change is a new file in `supabase/migrations/` named `<timestamp>_<name>.sql`, applied with the Supabase MCP `apply_migration`, then checked with `get_advisors` (security). Test RLS by impersonating `anon`/`authenticated` inside a transaction that rolls back.
The publishable key in the apps is public by design; security comes from RLS and the token-checking functions.

## 5. Build, test, ship
- `cd mobile && npm test` — unit tests for `src/features`.
- `cd mobile && npx tsc --noEmit` — typecheck. `npx expo lint` — lint.
- `cd mobile && npx expo export -p web` — web export used only for screenshot checks with Playwright (Chromium at `/opt/pw-browsers`). The real target is Android.
- **Android APK is built by GitHub Actions** (`.github/workflows/android.yml`): prebuild → Gradle `assembleRelease` → APK attached to a GitHub Release `mobile-v<version>` and as a workflow artifact. The Claude sandbox cannot reach Google's Maven, so never try a local Gradle build here.
- Web (`web/`) deploys to Vercel automatically on push to `main` (site: https://coachflow-cyan.vercel.app).
- Commits end with the Co-Authored-By line from the session instructions. Push to `main` only after tests and typecheck pass.

## 6. Conventions
- Components are function components with hooks; styles via `StyleSheet.create` using tokens only (no raw hex in components).
- All strings through `t('key')`; add both `az` and `ru` in the same change.
- Money is AZN, shown as `120 AZN`; weights in kg with comma decimal in `ru`/`az` (`62,5`).
- Dates: week starts Monday; Asia/Baku.
- Accessibility: every icon-only pressable has `accessibilityLabel`; contrast ≥4.5:1 for body text.
- Do not add a dependency without checking an Expo module does not already cover it.
